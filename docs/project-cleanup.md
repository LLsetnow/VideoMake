# 项目中间产物分级清理规则

本文用于管理 `projects/` 下视频制作过程中产生的中间文件，在节约磁盘空间的同时保留项目的复现能力、最终成品和必要的核验依据。

清理默认是只读评估流程。任何实际处理（移入回收站、移动到外部归档或压缩），都必须先生成清单并由用户确认；不得因为文件名包含“中间”或“final”就直接判断其用途。

本规则中的“清理”默认只表示将文件移入 macOS 回收站，不表示永久删除。禁止使用 `rm`、`rm -rf` 或其他不可恢复的直接删除命令。回收站未被用户清空前，文件应保持可恢复；因此清理报告要区分“移入回收站的可用空间”和“清空回收站后的实际释放空间”。

## 核心原则

1. 最终成品、可复现所需的 Prompt/Workflow、唯一源素材和制作记录优先于节省空间。
2. 先确认项目状态和依赖关系，再按级别处理；文件名只是候选信号，不是移入回收站的依据。
3. 先校验再清理：最终视频至少通过 `ffprobe`、可读性和音画检查；重复文件必须通过内容哈希确认。
4. 有效的 `videoOutput/` 软链接引用的文件不得移入回收站或移动。软链接状态必须使用 `readlink` 和 `[ -e ]` 检查，不能只看链接名称。
5. 不将项目中唯一的源音频、参考图、角色身份图、工作流、提示词、制作记录或最终核验记录移入回收站。
6. 工作区存在未提交改动时，先记录 `git status --short`，不要把清理产生的文件变化混入其他变更；涉及 Git 追踪文件时必须单独确认范围。
7. Cookie、登录令牌、API 密钥和其他凭据不属于项目资产，必须被忽略或移出仓库，不能通过清理规则归档进项目。

## 清理动作定义

- **移入回收站**：本文及未来清理工具的唯一自动处理动作。使用 macOS Finder/系统回收站 API 或经过验证的 `trash` 工具，并保留清单中的原始路径、文件大小和哈希记录。
- **外部归档或压缩**：只有在用户明确指定归档目录并单独确认时才执行；它不是自动清理动作。归档成功并完成校验后，工作区副本如需移出，也只能移入回收站。
- **永久删除**：不属于本规则的操作。不得调用 `rm`、`rm -rf` 或其他不可恢复删除命令；是否清空回收站由用户在 Finder 中自行决定。

## 保留级别

| 级别 | 含义 | 典型内容 | 默认策略 |
| --- | --- | --- | --- |
| P0 | 永久保留 | 已验收/已发布最终成片、封面、README、制作方案/记录、最终 Prompt、最终 Workflow、最终 QA 报告和必要的最终联系表 | 不自动处理 |
| P1 | 重要复现素材 | 唯一源音频、唯一参考图/角色图、参考视频、用于最终剪辑的 H3 片段、最终剪辑清单、帧级时间轴和关键分析结果 | 项目完成后继续保留；必要时转外部归档 |
| P2 | 可压缩或归档 | 旧版成片、备用版本、重复复制的音频切片、未选中的可用生成结果、重复 QA 图片 | 先去重；保留外部归档或压缩包后再移出工作区或移入回收站 |
| P3 | 验收后可清理 | `中间文件/`、`拼接中间文件/`、`qa/trimmed/`、逐段 QA 视频、`video_only`、`conditioning`、`padded`、`ComfyUI_*`、`prefix`、`suffix`、`replacement`、未采用的 beat-lock 分段 | 成片验收并确认可重建后移入回收站 |
| P4 | 可立即重建或无长期价值 | `.DS_Store`、缓存、失败输出、临时解码检查文件、临时日志、失效引用 | 确认无依赖后优先清理 |

级别不是仅由扩展名决定。例如，一个 `mp4` 可能是 P0 最终成片，也可能是 P3 的拼接中间文件；一个 `txt` 可能是 P0 的提示词，也可能是 P4 的一次性日志。

## 文件和目录判断

### P0：必须保留

每个已完成项目至少应保留：

- 项目 `README.md`、制作方案、制作记录或等价的复现说明；
- 最终采用的英文 Prompt、中文翻译（如有）和 `*_workflow_api.json`；
- 项目最终成片，通常位于项目的 `output/`，或项目文档明确指定的最终输出目录；
- 封面、最终使用的独立源音频和不可替代的参考图；
- 最终 `ffprobe` 记录、帧数/音频核验报告、最终联系表或等价证据；
- 与最终成片对应的 `videoOutput/` 有效软链接。

如果一个项目有多个“最终版”，必须在项目 README 或制作记录中指定唯一的当前交付版。其他版本降为 P2，不得全部按 P0 永久保留。

### P1：保留或外部归档

以下内容通常是重新生成、重新剪辑或解释结果时需要的依据：

- 原始或锁定源音频，以及无法从仓库外可靠获取的音频切片；
- 角色身份图、场景图、首帧/尾帧和唯一视觉参考图；
- 参考视频：若只用于离线分析且能通过稳定来源重新下载，可在记录来源和授权后降为 P2；否则保留；
- 被最终时间轴实际使用的生成片段；
- `analysis/`、`01_参考分析/` 中支撑最终剪辑的鼓点、场景检测、素材清单和时间轴；
- `cutlist.csv`、`beat_locked_timeline.csv`、`asset_manifest.csv` 等能够说明素材选择和帧边界的清单。

如果源素材已经在仓库外的稳定位置保存，项目中仍应保留来源、路径、时长、哈希或下载说明，不能只把文件移入回收站而不留下来源记录。

### P2：去重或压缩

处理 P2 时，优先使用内容哈希和引用关系，而不是手工猜测：

- 完全相同的音频切片只保留一个规范路径，其他位置改为引用说明或软链接；
- 同一成片同时存在于项目根 `output/`、`04_输出/` 和其他备份目录时，指定一个规范实体；
- 旧版最终视频、修复前版本和备用版本移到项目外的归档盘，或压缩为带清单的归档包；不需要归档的副本移入回收站；
- 未被最终时间轴采用、且不再需要比较的生成结果可以归档，不要和最终成片并列长期保存；
- 联系表、缩略图和重复的 QC 图片可保留最终版，将同一阶段的重复版本移入回收站。

归档包必须附带项目名、归档日期、原始相对路径、文件哈希和恢复说明。压缩后不能只保留一个无法定位内容的无名压缩包。

### P3：验收后清理

以下路径或命名是 P3 候选，但每个文件都必须先做依赖检查：

- `output/中间文件/`；
- `04_输出/拼接中间文件/`；
- `qa/trimmed/`、`qa/beat_locked_segments/` 和逐段 QA 视频；
- `*_video_only.mp4`、`视频画面_only*.mp4`；
- `*conditioning*`、`*padded*`、`ComfyUI_*.mp4`；
- `prefix_*.mp4`、`suffix_*.mp4`、`replacement_*.mp4`、`redo_*`；
- 已经用于生成最终成片的旧分段拼接文件和重复导出文件；
- 仅用于一次性检查的中间 `contact_sheet`，但最终联系表和最终核验图应保留。

P3 文件只有在以下条件同时满足时才能移入回收站：

1. 项目有明确的 P0 最终成片；
2. 最终成片已通过时长、帧率、画幅、音轨和可读性检查；
3. 拟移入回收站的对象不被最终 Workflow、Prompt、剪辑清单、脚本或 `videoOutput/` 软链接引用；
4. 移入回收站后仍能解释最终成片的来源和制作路径；
5. 如果文件是唯一的中间备份，已确认不需要回滚或重新比较；
6. 清理清单已记录路径、大小、级别、移入回收站理由和预计可用空间。

### P4：优先清理

P4 仍然需要先确认没有引用，但通常可以在项目完成后立即处理：

- `.DS_Store`；
- 失败的生成输出、失败任务留下的空文件和临时导出；
- 一次性 `decode_check.txt`、临时日志和不再使用的调试报告；
- 已确认失效且没有恢复价值的项目内引用。

Cookie、令牌和密钥不应等待 P4 清理，而应在发现时立即从仓库追踪范围移除，并加入 `.gitignore`。

## 项目生命周期策略

### 生成中

保留 P0、P1，以及当前任务所有 P2/P3 候选。生成或剪辑未完成时，不将片段、源音频、分析文件和任何备用输出移入回收站。

### 初次验收通过

先把最终成片、最终 Prompt/Workflow、源素材、最终 QA 和制作记录标记为 P0/P1，再将未采用的生成结果和中间拼接文件标记为 P2/P3。此时只进行 dry-run，不自动移入回收站。

### 发布或交付完成

确认发布平台使用的文件与本地 P0 成片一致后，可以将符合条件的 P3 候选移入回收站；P2 保留 30–90 天，之后根据是否仍需修改决定是否进行外部归档，工作区副本仍只能移入回收站。

### 项目归档

项目只保留 P0 和必要的 P1。P2 如需长期保留，放入带清单的外部归档；P3/P4 在确认无依赖后移入回收站。若未来仍可能重做，至少保留源音频、最终 Workflow、Prompt、参考图和制作记录。

## 清理前检查流程

清理工具或手工操作必须先完成以下只读步骤：

```bash
# 1. 确认工作区没有未识别的改动
git status --short -- projects videoOutput

# 2. 统计项目和候选文件
du -sh projects/*
find projects -type f \( -name '*.mp4' -o -name '*.wav' -o -name '*.mp3' -o -name '*.m4a' \) -print

# 3. 检查最终软链接
find videoOutput -maxdepth 1 -type l -print
readlink videoOutput/<最终文件名>
test -e "$(readlink videoOutput/<最终文件名>)"

# 4. 对最终成片做基本媒体核验
ffprobe -v error -show_format -show_streams "projects/<项目>/output/<最终成片>"
```

随后生成清理清单，至少包含：

```text
项目路径 | 文件路径 | 级别 | 文件大小 | 是否被引用 | 是否重复 | 移入回收站/归档理由 | 预计可用空间
```

默认执行顺序为：P4 → 已确认重复的 P2 → 已验收的 P3 → 到期的 P2。P0 和未确认的 P1 不进入自动移入回收站清单。

## 去重和 Git 注意事项

- 只有内容哈希一致时才可视为重复；同名、同尺寸或相似命名不足以证明重复。
- 去重后必须保留一个规范路径，并更新 README、清单或脚本中的引用。
- 将 Git 追踪文件移入回收站会在工作区产生删除变更，但不会自动移除 Git 历史中的大文件；本规则不直接运行 `git rm`。若目标是缩小仓库克隆体积，还需要单独规划 Git LFS 或历史重写，不能把它和普通项目清理混在一起。
- 当前仓库如果有未提交的用户文件变化、重命名或生成任务，清理工具不得自动暂存、提交、恢复或推送这些变更。

## 推荐的工具接口

后续如实现清理工具，默认应提供以下只读模式；这些命令目前只是接口约定，不代表仓库已经安装对应 CLI：

```bash
cleanup-projects --dry-run --level P4
cleanup-projects --dry-run --level P3 --project '<项目名>'
cleanup-projects --dry-run --duplicates
cleanup-projects --apply --manifest '<已确认的清理清单>'
```

任何 `--apply` 操作都应要求清单文件、显示总文件数和预计可用空间，并在移入回收站前再次检查有效软链接、Git 状态和文件哈希。`--apply` 只能将确认过的文件移入 macOS 回收站，不得调用 `rm`、`rm -rf` 或其他永久删除命令。移入回收站后是否清空，由用户自行决定。
